# Notes

Register values, gotchas, and the things that turned out to be wrong. The build
and the boot are in [README.md](README.md).

## Reading the ADT

```sh
ipsw extract --pattern 'DeviceTree.*' -o work <ipsw>
pyimg4 im4p extract -i work/*/Firmware/all_flash/DeviceTree.d331pap.im4p \
    -o build/adt-d331p.bin
cd build/m1n1/proxyclient
../../venv/bin/python -c '
from m1n1.adt import load_adt
adt = load_adt(open("../../adt-d331p.bin", "rb").read())
for c in adt["/arm-io/usb-complex"]:
    print(c._path, [hex(c.get_reg(i)[0]) for i in range(len(c.reg))])'
```

Each `reg` is an offset from its parent's base, and it nests: `/arm-io` sets the
window from its `ranges`, so `usb-complex` at `0x39000000` is really
`0x239000000`, and `usb-device` at `0x100000` under it is `0x239100000`. The raw
`reg` gives the second number silently. `get_reg()` walks `ranges` up the tree
and gives the first. Use it.

`dts/t8020-pmgr.dtsi` is generated by `make pmgr DT=<DeviceTree im4p>`, not

blocks, so that board is a second `.dts` when someone wants it.

## CPU affinity

CPU `reg` must equal `MPIDR_EL1 & 0xFFFFFF`, and the ADT's `reg` is not that
number: it reports 0 for cpu0 and 256 for cpu4, dropping the Aff2 bit. The boot
core reports MPIDR `0x80010100`, so cluster 1 core 0 is `0x10100` and the E
cores are `0x0` to `0x3`. Take the ADT values literally and m1n1 prunes all six
CPU nodes, including its own, leaving Linux a tree with no CPUs.

## The two consoles

- **Output.** The framebuffer m1n1 hands over, as `apple,simple-framebuffer`
  plus `console=tty0`. No display driver, so the picture is frozen as handed
  over. The node needs `power-domains`, or `apple-pmgr-pwrstate` powers down
  `ps_disp0_be`, `ps_mipi_dsi`, `ps_disp0_hilo` and `ps_disp0_ppp` as unused and
  the display appears to die mid-boot.
- **Input.** A USB CDC-ACM gadget the initramfs brings up, which is why the tree
  needs the USB complex, PHY, dwc2, the DART and the PMGR domains.

UART0 exists and `earlycon` uses it, but it needs a serial cable on the
Lightning pins.

The console used to paint behind the notch. `get_notchless_fb()` in m1n1 looks
for `partially-occluded-display` on the ADT's `/product` node, which D331p does
not have, and then falls back to a list of T8015 board ids. `patches/m1n1-0011`
adds this board, 0x1a, with a notch of 132 pixels, which is the 44pt safe area
inset at 3x. The phone reports `1242,2556` in
`/sys/class/graphics/fb0/virtual_size` with it, down from 2688.

The aspect ratio trick the generic path uses does not work here: it computes
16:34 and trims 49 pixels, which is not the notch.

`tools/tsh.py` runs one command on the telnet shell and prints the reply, so a
boot can be checked without a terminal. `telnetlib` left the stdlib in 3.13 and
all this needs is to refuse every option, so the negotiation is inline.

## Reaching the shell

The phone is `172.16.42.1`, runs `telnetd` on port 23, and hands the host
`172.16.42.2` over DHCP. There is also a getty on `/dev/ttyGS0`, the phone's
`05ac:4142` `/dev/ttyACM*`. It blocks on a read before printing, so a silent ACM
port is not a fault.

## Boot chain

`make boot` drives all of this, and `make images` builds the one-time pieces
from an unpacked IPSW. Underneath, `tools/dfuboot.py` sends the patched iBSS
over the pwned DFU protocol, which is three control requests, see below. The
ROM exploit jumps to the uploaded image unconditionally, no signature and no
patching needed for that step. The phone's USB device changes from `05ac:1227`
(DFU) to `05ac:1281` (recovery) and `irecovery -q` answers for real
(`PRODUCT: iPhone11,6`, `MODEL: d331pap`). iBSS is alive and DRAM is up.

From there it is Apple's own recovery protocol. The pwned-DFU custom requests
are gone, this is genuine Apple code running. `irecovery -f` stages a component
and `bootx` validates and jumps to it.

iBSS and iBEC on this board are not encrypted (`ipsw img4 im4p info` reports
`"encrypted": false`), only LZFSE compressed, so `ipsw img4 im4p extract` gives
the plain binary and there is no GID key dance. Nothing here needs the
exploit's `kbag` or AES requests.

Keeping iBSS in the chain is what keeps the on-screen console: iBoot
initialises the display and `console=tty0` inherits that framebuffer.

### The image4 patch was aimed at the wrong function

`iboot_patcher.py` applies its "image4 callback" patch at file offset `0xE10`.
That is not image4. It is a stack cookie check:

```text
ldr  x9, [x9]
cmp  x9, x8
b.ne ...
```

so the patch NOPs a stack protector in an unrelated function and forces a
return value, which is why it never helped and why patched images were flaky.
The real `_image4_validate_property_callback` on this build is at `0x2BF20`.
`iboot_patchfinder.py` in the same tree names it correctly, and hBootPatcher
agrees from the other side: it finds the `EKEY` literal at `0x2C31C`, which is
inside that function.

`tools/iboot-image4-patch.py` finds it from the `EKEY` anchor and writes
`mov w0, #0` / `ret` over the entry. hBootPatcher cannot patch this firmware at
all, and the reason is worth recording: it walks forward from the anchor looking
for a `ret`, but iBoot is PAC signed now and returns through `retab`, so it
bails with "failed to find image4_validate_property_callback function return".
Walking back to the opening `pacibsp` instead is version independent.

### A manifest has to be present, even a wrong one

There is a single verdict branch above all of this, at `0x5C530`, inside the
validator at `0x5C418` that both `go` and `bootx` call:

```text
mov w0, #0
tbz w19, #31, <success>
```

Forcing that branch does make iBoot accept a container with no IM4M at all, and
both "Memory image not valid" and "Kernelcache image not valid" stop appearing.
It is still the wrong patch. The verdict is computed after the payload would
have been extracted, so skipping it leaves iBoot carrying on with nothing
unpacked, falling over the moment it uses the result. The crash lands right as
the upload completes, which reads like a size or transfer problem and is not
one.

So the manifest is load bearing as structure, not as proof. The three states,
all measured:

| patch | manifest | what happens |
|---|---|---|
| verdict at `0x5C530` | none | accepted, nothing extracted, crash |
| callback at `0x2BF20` | borrowed | "image not valid", device survives |
| callback at `0x2BF20` | borrowed, plus the real fix | boots |

The IM4M templates run `0x7000` to `0x8960` with no `0x8020`. That is not an
oversight: from A11 on the manifest is tied to the device's own ECID, so no
generic template can exist. It does not need to. `0x8015.im4m` works as filler,
because once the property callback always succeeds, every check that would
notice the manifest belongs to another chip is a check that no longer runs.

### The payload is a Mach-O, and three stages come first

`bootx` wants an Apple kernelcache, so the blob has to start with
`m1n1-idevice.macho`, not `m1n1.bin`. A raw image is rejected without a word.

It also needs the two stages before it, which is what makes `bootx` fail
silently when they are missing: devicetree as `rdtr` then the `devicetree`
command, an empty trustcache as `rtsc` then `firmware`, then the payload as
`rkrn` and `bootx`. Compress the kernelcache with `lzss`, which `--extra`
requires anyway for the monitor stub.

The trustcache is 24 bytes: version 1, a uuid, zero entries. Nothing checks the
uuid.

Two things that cost time and are easy to re-trip:

- iBSS and iBEC extract to byte-identical binaries here, same md5. Only the
  img4 type tag differs, so there is no second banner to tell you iBEC took
  over, and no reason to send it at all.
- Uploading anything while the phone is still in DFU corrupts the exploit's
  request handler, and the next upload jumps into garbage.
  `tools/iboot-boot.sh` checks the mode before every send for this reason.

### The USB domains are down coming from iBSS

m1n1 took a data abort in `usb_init()` on the first register read of the dwc2
core, `read32(regs + DWC2_GSNPSID)`, FAR `0x239100040`. The core was not
powered.

Three domains matter, and Linux names all three on the way up:

```text
always-on domain usb is not on at boot          802a8
always-on domain usbctlreg is not on at boot    802b0
always-on domain usb2dev is not on at boot      802c0
```

`patches/m1n1-0001` adds `0x802c0` and power cycles all three from the T8020
case. With it the abort is gone, m1n1 reports `USB0: initialized`, and those
three warnings disappear from the Linux log too, because the domains are
already up by the time Linux looks.

Skipping `usb_init()` for T8020 also stops the abort and was tried first. It is
the wrong fix: m1n1 is what powers and remaps the complex for Linux, so
skipping it leaves Linux with USB down and no gadget.

### The pwned DFU protocol

The exploit leaves the standard DFU download request in place and adds two of
its own, all on `bmRequestType` 0x21:

| request | what it does |
|---|---|
| 1 | `DFU_DNLOAD`, up to 0x800 bytes a time, zero length ends the transfer |
| 6 | `DFU_ABORT` |
| 7 | demote the chip, not needed here |
| 8 | jump to the image just uploaded |

The device stops answering partway through request 8, which is the jump, not a
failure.

### RP2350 firmware

The jig is a Pico 2 W running usbliter8 and nothing else. Plug a phone in DFU
into it and the exploit fires on its own in about a second, leaving the phone in
DFU with a patched request handler. Move the cable to the PC and everything
after that talks to the phone directly.

Build it from source, there is no release for this board:

```sh
cmake -S . -B build -DPICO_BOARD=pico2_w -DPICO_PLATFORM=rp2350
cmake --build build -j
```

It needs `PICO_SDK_PATH` at pico-sdk 2.2.0 or newer, because `pico_status_led`
does not exist before it, and `PICO_TOOLCHAIN_PATH` at an arm-none-eabi GCC.
Gentoo packages neither, so both live under `3rd-party/` by hand. On 2.2.0 the
`pico2_w` board pulls in `pico_status_led`, which needs the `cyw43-driver`
submodule even though the radio is never touched:

```sh
git submodule update --init --depth 1 lib/cyw43-driver
```

`boards/pico2_w.cmake` is ours: same PIO pins as a Pico 2, no LED definitions,
because the W's LED hangs off the radio rather than a GPIO. `led.c` has an empty
fallback for that, so progress is read over the USB serial port instead. Flash
by holding BOOTSEL and copying `build/usbliter8.uf2`, or with
`picotool load -t elf build/usbliter8.elf -x -f`.

### Checking the phone is pwned

```console
$ cat /sys/bus/usb/devices/*/serial
CPID:8020 ... BDID:1A ... SRTG:[iBoot-3865.0.0.4.7] PWND:[usbliter8]
```

`CPID:8020` is the chip, `BDID:1A` the D331pAP board. `PWND:[usbliter8]` is the
whole test: with it the phone takes an image, without it the exploit has not
run. Product id 0x1227 is DFU, 0x1281 recovery.

## m1n1 patches

Twelve, in `patches/`. Nine are T8020 support, three are about seeing anything.

- **`0001` USB complex registers.** `usb-complex,t8020` fell through to the
  `t8011` case and took its DMA remap offsets.
- **`0002` SError handling.** An asynchronous SError fires at the top-of-RAM
  boundary (`L2C_ERR_ADR` `0x8ec78c000`) every boot. m1n1's clear was
  `reg_mask(..., ACCESS_FAULT | PIO_FAULT, 0)`, a write of zeroes, but the
  register is write-1-to-clear (`ENABLE_W1C`, bit 56). Writing ones to the fault
  bits, `RECURSIVE_FAULT` included, works. Root cause unknown. Masking DAIF does
  nothing: ERET restores SPSR.
- **`0005` A12 MIDR parts.** `midr.h` defined `MIDR_PART_T8020_VORTEX` and
  `_TEMPSET` but nothing used them, so the lookup fell back to
  `features_unknown` with `apple_sysregs_unlocked` false, sending an A12 down an
  M4-only path that reads `CTRR_M4_LWR_EL2` from EL1.
- **`0007` dwc2 DMA coherency and PHY width.** Two bugs. Nothing in the USB path
  snoops, not the remap widget and not the DART behind it, so with caches on the
  CPU reads stale SETUP packets and never answers. m1n1 now invalidates before
  reading and cleans before handing a buffer over. Separately `usb_dwc2_init()`
  read `PHYIF16` just after `usb_bringup` reset the PHY, saw it clear, and
  picked the ULPI 8-bit turnaround. Both look identical from the host: attach,
  chirp, then `device descriptor read/64, error -110`.
- **`0008` CPU start offset** and **`0009` A12 chicken bits**, see [SMP](#smp).
  `0005` also carries the table hook-up for `0009`, since both touch the same
  lines and `make patch` checks each patch alone.
- **`0010` USB power domains**, **`0011` dwc2 errors to the framebuffer** and
  **`0012` the USB DART**, see [USB](#usb). `0012` is what made the gadget
  enumerate, and it also takes the remap splice value back out of `0001`.

`0003`, `0004`, `0006` exist because the framebuffer is the only console without
a serial cable, and a `RELEASE` build defines `FB_SILENT_MODE`, which silences
it when a payload is present.

## USB

### The DART, and the AHB error on every DMA

The gadget enumerated from nothing for a long time. Both drivers failed the same
way, m1n1's proxy and Linux's dwc2, so the fault was below both. Host side:

```text
usb 3-2: new high-speed USB device number 60 using xhci_hcd
usb 3-2: device descriptor read/64, error -110
usb usb3-port2: unable to enumerate USB device
```

Device side, which took a while to be able to see at all:

```text
GINT=04001020                       USBRst
GINT=04002020                       ENUMDone
GINT=04088028 DAINT=00010000        OEPInt, so a SETUP did arrive
  DOEPINT0=0000800d   StupPktRcvd | SetUp | AHBErr | XferCompl
  DIEPINT0=00002094   NAKIntr | TxFIFOEmpty | IntknTXFEmp | AHBErr
usb-dwc2[ERR]: BAD STATUS with COMPL now with STATE_SETUP_PENDING, doepint=1
```

`AHBErr` in both directions. The controller takes a bus error the moment it
tries to DMA the SETUP packet, so ep0 is never re-armed: `DOEPCTL0` goes
`80028000` to `00028000` to `00008000` and `EPENA` never comes back. Linux ends
up in the same place, `DOEPCTL=0x00028000` with `EPENA` clear and `DAINT=0`,
which is why its ep0 is deaf and `USBRST` sits pending.

It was the DART, which this tree had been ignoring.
`/arm-io/usb-complex/usb-device` has an `iommu-parent` pointing at
`/arm-io/dart-usb/mapper-usbdev`, stream 0, and EHCI and OHCI have their own
mappers next to it. iBSS leaves that DART in bypass, `TCR=0x100`, and bypass
here does not mean passthrough: the 32 bit address the controller emits never
becomes an address in DRAM, which starts at `0x800000000`, so the fabric answers
with an error.

`m1n1-0001` initialises stream 0 and flat maps DRAM at the low 32 bits of each
page's own address, which is what the driver writes into `DOEPDMA` and
`DIEPDMA`. On the Linux side `dart_usb` is a node in `t8020.dtsi` with
`iommus = <&dart_usb 0>` on `usbdev`, so `apple-dart` does the same job through
the DMA API:

```text
apple-dart 239900000.iommu: DART [pagesize 4000, 16 streams,
  bypass support: 1, bypass forced: 0, AS 32 -> 36] initialized
platform 239100000.usbdev: Adding to iommu group 0
```

The `dma-ranges` that used to be on the complex bus is gone with it. It mapped
DMA address 0 to the start of DRAM, which is what the DART does now, and an
offset like that on an IOMMU translated device only confuses the DMA layer.

Ruled out on the way, none of it worth retrying: interrupt affinity (the line is
delivered on CPU0 and CPU1 alike, `spurious count 0`), console load (a quiet
`loglevel=4` boot fails the same), mode drift (`curmod=0` throughout, and
`GUSBCFG` bit 30 and the `SIG` role field at `7 << 20` both refuse writes),
writing all three remap triplets instead of just the device one, and DMA address
truncation. A trace right after the write read back `DOEPDMA=11fd8000` for a
buffer at `0x811fd8000`, exactly the low half, so that write lands as designed.

### Complex and widget registers

The ADT lists `usb_widget_with_mask` as three (offset, value, mask) triplets at
0x28, 0x38 and 0x48, value 0x88, mask 0x030000ff. Only 0x48, the device
controller, matters here. Live values from a working boot:

```text
0x239000000: 1           complex enable
0x239000048: 03000000    device widget
```

The widget is not an address adder with an enable. The low byte is a value it
splices into bits 35:32 of every address the controller emits, and the two bits
the mask covers above it, 24 and 25, are the DMA enables for the two directions.
Clearing those two on a live gadget, by poking `0x88` in from the m1n1 proxy,
left the device enumerated on the host and killed every transfer.

The widget sits in front of the DART, so whatever it splices in is what the DART
needs a mapping for. That settles the value: zero. With `8` in there the DART
has to answer for `0x8_11fd8000`, and no Linux DMA address can ever reach that,
because dwc2 is a 32 bit master and asks for a 32 bit mask.

### AUSB SIG bits are shifted on T8020

The PHY reads `0x00d10003` with a cable, which is m1n1's documented `0xd103`
with every upper bit moved up by 8:

| | bits set |
|---|---|
| m1n1 `0xd103` | 0, 1, **8, 12, 14, 15** |
| T8020 `0x00d10003` | 0, 1, **16, 20, 22, 23** |

So `AUSB_SIG_CABLE_CONNECTED` is `BIT(16)` not `BIT(8)`, and `AUSB_SIG_HOST` is
`7 << 20` not `7 << 12`. The Linux `ausb` driver tests bit 8 and never sees a
cable. VBUS detection has to stay forced (`AUSB_SIG_VBUSDET_FORCE_EN`); the PHY
then reads `0x01c10003`, which m1n1 calls "USB proxy active".

### dwc2 writes never landed

Every dwc2 write was dropped while every read worked:

```text
wtest GAHBCFG  00000000 -> 00000000 (wrote 0000002e)
wtest DCTL     00000002 -> 00000002 (wrote 00000000)
```

Missing `nonposted-mmio` on `bus@239000000`. `of_mmio_is_nonposted()` only
checks the node and its immediate parent, so the one on `soc` does not reach a
bus further down, and the PHY and dwc2 got `ioremap()` instead of
`ioremap_np()`. Upstream repeats the property on this bus for every A-series
SoC. With it added the writes land, which explains every earlier dead end at
once: they were all writes into a block that was not listening.

Ruled out before that was found: hardware (same PC, same cable, a different
stack enumerates), complex enable (reads `0x1`), the widget (0x48 reads back),
PHYIF16 (`0x1408`), an SError storm, the core soft reset, the USB power domains
(read `0xff`), `PCGCTL` clamp (reads 0), a high-speed-only fault, cache
maintenance, and dwc2's own mapping (a second `ioremap()` behaved the same).

### The gadget prints are load bearing

The `dev_info` calls `linux-0002` adds to `dwc2_hsotg_udc_start()` and
`dwc2_hsotg_pullup()` look like leftover debugging. Removing them, nothing else
changed, stops the gadget enumerating: `new device is high-speed` and then the
`-110` timeout. They are delays wearing a print's clothing, each one costing
milliseconds on the 155x168 simpledrm console, and they are the only thing
between `dwc2_force_mode()`, `dwc2_hsotg_core_connect()` and the manual
`DCTL_SFTDISCON` clear. The real fix is an explicit delay at whichever gap
matters, one DFU cycle per guess. Until then, leave all six.

### Timing, and where the cable is

The cable moves from the jig to the PC after the exploit and before iBSS runs,
so nothing has bound a gadget yet when it moves. Binding on the jig and moving
afterwards does not work: the host sees the attach and the chirp, which is the
PHY, then times out on every control transfer.

Two more timing traps. A diagnostic loop polling the gadget every 100ms was
itself enough to stop enumeration, because a host will not wait that long for
ep0. And m1n1's USB is polled from `uartproxy_run()`, so anything hogging the
CPU in m1n1 looks like broken USB.

### The gadget often never takes an address, worked around

The root cause is still unsolved, but the boot is no longer a coin flip: the
gadget now replugs itself until the host accepts it, see
[self replug](#the-self-replug) below. What follows is the failure itself.

The phone reaches a shell every time, the gadget binds, the host resets the bus
twice, and then the device is never addressed.

Host side:

```text
xhci_hcd 0000:0a:00.3: Timeout while waiting for setup device command
usb 3-2: device not accepting address 93, error -62
usb 3-2: Device not responding to setup address.
usb 3-2: device descriptor read/64, error -71
usb usb3-port2: attempt power cycle
usb usb3-port2: unable to enumerate USB device
```

Device side, from a one-shot report ten seconds after the pullup:

```text
apple: irqs=5 setups=0 last=00 00 0000
apple: DSTS=0004a200 DCFG=00840000 GINTSTS=04008028 DAINT=00000000
apple: DOEPINT0=00002010 DIEPINT0=00002080 DOEPCTL0=80008000 DIEPCTL0=00028000
apple: DAINTMSK=00010001 DOEPMSK=0000022f DOEPTSIZ0=20080008
```

`DOEPINT0` bit 4 is `OUTTknEPdis`, an OUT token arriving while the core treats
the endpoint as disabled, and `DOEPCTL0` reads `EPENA` set at the same time. So
the driver and the core disagree about whether ep0 is armed, while `DSTS`
SOFFN keeps advancing, which means the PHY is receiving. `DOEPTSIZ0` is exactly
what the driver programs for a SETUP, `SUPCNT=1 PKTCNT=1 XFERSIZE=8`.

On the boots that get further, the first `GET_DESCRIPTOR` is answered properly
and the failure moves one step later: `setups=1 last=80 06 0100`, the 18 byte
reply queued on ep0 IN with `EPENA` set and no "failed to become enabled", and
then nothing after the host's second reset.

Tried and ruled out, so none of it is worth repeating:

- **The DMA path.** The SETUP arrives and parses correctly, so the inbound DMA
  lands. Forcing the gadget to PIO (`p->g_dma = false`) fails the same way,
  with the packet arriving and `WARN_ON_ONCE` in `dwc2_hsotg_rx_data()`
  instead. `DOEPDMA0` reads back values that are not any address the driver
  programmed, so that register is not worth reading here.
- **Re-priming the control request.** `dwc2_hsotg_enqueue_setup()` returns
  early when the request is still queued, which looked load bearing and is
  not.
- **`hsotg->connected`.** It only becomes true on `SET_ADDRESS`, so the reset
  handler skips both `dwc2_hsotg_disconnect()` and the core re-init before the
  first successful enumeration. Setting it at EnumDone gave one clean boot and
  then failed. Re-initialising on every reset instead made it worse: the core
  stopped reporting resets at all.
- **A forced disconnect edge.** 120ms of `DCTL_SFTDISCON` before connecting, on
  the theory that D+ had been up since iBSS so the host saw no new connect. No
  effect.
- **m1n1's own gadget.** `kboot_boot()` calls `usb_init()`, so m1n1 hands over
  with `1209:316d` live on the port. Skipping that and leaving the complex, PHY
  and DART up gave one textbook boot, address assigned 52us after the second
  reset, then failed on the next.
- **The host port.** Moving to another port changes nothing, in both
  directions.
- **Clocks and power domains.** `clk_ignore_unused pd_ignore_unused`, confirmed
  active on screen as "Not disabling unused clocks", fails the same way. That
  hypothesis predicted a deterministic fix, so it is properly dead.

**Method note, learned the expensive way.** At this failure rate a single boot
proves nothing, and several "fixes" here looked right for exactly one boot
before failing on the repeat. Anything claimed about this needs a run of boots
per configuration, which is the real cost: every one is a DFU trip by hand.

### The self replug

Pulling the cable out and pushing it back in always fixes the boot, however
many tries it takes. Soft disconnect is that replug from this side, so a
delayed work does it on a timer, every 3s, up to 10 passes, with three states:

| state | what the work does |
|---|---|
| `gadget.state` is `USB_STATE_CONFIGURED` | stop, the link is up |
| `DCFG` device address is not zero | wait, the host is partway through |
| no address | toggle `DCTL_SFTDISCON`, 20ms apart |

The address is the wrong stop condition on its own: the host assigns one, fails
the descriptor read anyway, and resets the port, which puts the address back to
zero. An earlier version watched only the address and tore down sessions that
were about to configure.

Five boots in a row came up with nobody touching the cable, at 2, 10, 8 and 10
passes, between 5s and 35s from power on. Before this, about half of boots
needed several replugs by hand and some never came up at all.

The log of a normal boot now reads:

```text
dwc2 239100000.usbdev: apple: no address, replug 1
dwc2 239100000.usbdev: apple: no address, replug 2
dwc2 239100000.usbdev: new address 2
dwc2 239100000.usbdev: apple: configured after 2 retries
```

Sometimes `new address 2` lands in the same microsecond as a replug: the SETUP
was already received and the driver had not written `DCFG` yet when the work
read it. It costs that session and the next pass picks it up, so it is not
worth another check.

Four `dev_info` calls used to sit in `dwc2_hsotg_udc_start()` and were load
bearing: with them the gadget enumerated, without them the host gave up with
`device descriptor read/64, error -110`. The console is a 155x168 simpledrm
framebuffer, so each line cost milliseconds, and simpledrm paints in bursts, so
how much delay you got varied per boot. They are `mdelay(50)` now, which is the
same delay without the superstition. `mdelay` and not `msleep`, because the
caller holds `hsotg->lock` with interrupts off.

### Everything this driver printed was invisible

m1n1's `usb_error_printf` went to `uart_printf`, and the dwc2 poll runs inside
an iodev callback, so `in_iodev` is set and `iodev_console_write()` sends it to
`IODEV_UART` and `IODEV_DOCKCHANNEL_UART` only. Without a serial cable on the
Lightning pins that is nowhere. The `BAD STATUS with COMPL` line above had been
printing all along. `patches/m1n1-0010` sends errors to `fb_console_write()` as
well, which is the only reason any of it was readable. Anything else that needs
watching from inside that callback needs the same treatment.

## No AIC interrupt is ever delivered

genpd powered the interrupt controller off. The AIC driver is registered with
`IRQCHIP_DECLARE`, long before the driver model, so it never becomes a consumer
of `ps_aic`, and "Disabling unused power domains" switches it off. After that no
interrupt is delivered and any AIC register read hangs the core, with no oops.
The boot still looks healthy because the timer is a core-local FIQ off AIC
entirely, so userspace, DHCP and the shell all come up with every device
interrupt missing.

Upstream marks the domain always-on as a core device; the generated pmgr dtsi
has no such property, so three lines in `dts/t8020.dtsi` fix it:

```text
&ps_aic {
    apple,always-on;
};
```

Any domain whose consumer is not a normal platform driver hits this. The clue
was that a read of any AIC register in a delayed work item hung the boot while
the same read works at init: a block that answers at init and hangs later has
been powered down in between.

Established about AIC:

- `AIC_WHOAMI` reads 4 on the boot CPU, which is logical CPU 0, so the two
  numbering schemes disagree. Upstream only warns; `0003` adds the mapping.
- `nr_irq` is 512 while the driver hardcodes `max_irq` 1024, and 1024 is
  correct: `mask_set` at `0x3880` reads 0 and the live registers are at
  `0x4100`/`0x4180`.
- `TARGET_CPU` is a mask over AIC's own numbering, so it is `BIT(AIC_WHOAMI)`
  for the programming core, not upstream's `BIT(0)`. `BIT(0)` aims everything at
  a Tempest core and even the mailbox stops.
- Reading `0x4200` (`HW_STATE` in the driver's layout), or `TARGET_CPU` for some
  hwirqs, raises a synchronous external abort.
- `AIC_CONFIG` bit 0 is not needed. Linux works without it.

## SMP

Works, all six cores, no `maxcpus` and no `isolcpus`. A parallel `dd`/`find`/
`md5sum` load on all six finishes cleanly, and every core takes function-call
IPIs.

What it needs (`patches/m1n1-0008`, `0009`, `linux-0001`, `dts/t8020.dtsi`):

- **CPU start block is A11's, `pmgr + 0xd4000`.** `ApplePMGR` starts a core by
  writing `+4` and `+8 + 4 * cluster` off a base it keeps at object offset
  `0x26d0`; where that base comes from was not in the kexts, so it was tested,
  and `0xd4000` gets `Started.` for CPUs 0-3 and 5. T8020 has A11's PMGR layout
  generally, CPU and CPM power states at `0x80000` on both.
- **RVBAR is writable.** All six `cpu-impl-reg` RVBARs read back as m1n1's base
  with the lock bit clear.
- **MPIDRs** in the DT: E cores `0x0`-`0x3`, P cores `0x10100`/`0x10101`. The DT
  had the E cores at `0x1000x` and m1n1 refused to hand over.
- **CPU power domains** `ps_ecpu0..3`, `ps_pcpu0..1`, `ps_ecpm`, `ps_pcpm` are
  always-on, as T8015 marks them; before that genpd tried to switch off the boot
  core's cluster.
- **A12 chicken bits.** m1n1 set none. `0009` is the APPLEVORTEX block of XNU's
  `start.s` (xnu-6153), rdar titles included.
- **Fast IPIs.** The AIC node lists `"apple,t8015-aic"` before `"apple,aic"`, so
  Linux uses the per-core fast IPI registers (`IPI_RR_GLOBAL_EL1`) as on A11.
  Plain `"apple,aic"` IPIs were never shown to be broken, but this is what the
  hardware and upstream T8015 use.

What actually broke it was the USB PHY, not SMP. `ausb_phy_usb2_power_on`
(`linux-0001`) mapped the USB complex at `0x239000000` with a bare `ioremap`,
which is posted. Everything on that bus has to be non-posted; the parent node's
`nonposted-mmio` only applies to `devm_platform_ioremap_resource`. The posted
write to the complex CTL register raises an asynchronous SError. On a P core
nothing is reported, which is why UP never saw it. On an E core it is fatal
(`ESR 0xbc000000`, `L2C_ERR_STS` ACCESS_FAULT, `L2C_ERR_ADR` low 40 bits
`0x239000000`). The PHY powers on in a kworker at probe, about 0.31s, and again
at gadget bind, so the boot died at whichever of those landed on an E core. That
matches every symptom: random stop points around 0.3s or right after the gadget
comes up, fine with `maxcpus=1`, fine with `isolcpus=1`, fine with only the two
P cores. Fixed with `ioremap_np`.

What found it was a temporary `do_serror` hook that, on Apple cores, logged
`L2C_ERR_STS`/`L2C_ERR_ADR` (`sys_reg(3, 3, 15, 8, 0)`/`(3, 3, 15, 9, 0)`),
cleared them and set `PSTATE.A` in the saved frame so the kernel survived. The
logged pc landed in `ausb_phy_usb2_power_on`. Also learned on the way: the E
cluster DVFS block at `0x210e20000` faults on a read of `+0x58`; both clusters
come up in P-state 2 (`DVFS_STATUS` `0x22`).

No help for digging: scanning PMGR from Linux (unimplemented pages abort, some
stall the bus and freeze the CPU), and CPU hotplug (spin-table CPUs cannot come
online after boot).

## NVMe on T8020, ANS2 bring-up

Storage is NVMe behind the ANS2 coprocessor: SART, an RTKit mailbox, ANS2, then
`nvme-apple`, all in the Hoolock kernel and `config_16k`. The work was device
tree plus placing T8020 between T8015 and T8103.

It works, both ways. `nvme0n1` comes up with its GPT and APFS container, plus
seven small vendor namespaces. A 64 MiB read runs at about 467 MB/s and a 64
MiB write at about 132 MB/s, and a 4 MiB file written, unmounted, re-mounted
after `drop_caches` and hashed again comes back identical. Seven faults, each
hiding the next, in the order found.

Mount it as `mount -t ext4 /dev/nvme0n1 /mnt`. Without the type, busybox has
nothing to autodetect with and the mount fails silently.

### 1. iBoot leaves its own admin queue programmed

```text
assert failed: [7442]:cmd fetch error for host 0 Admin SQ, rresp code 2
```

`rresp` 2 is an AXI SLVERR. On entry to `apple_nvme_reset_work` the block still
held iBoot's values (`ASQ=0x8788e0000`), because the coprocessor reset does not
clear it, and that queue is no longer in the SART allow list. Writing our own
`AQA`/`ASQ`/`ACQ` before releasing the coprocessor fixes it.

### 2. The APCIe complex has to stay powered

```text
== Exception taken from EL1h ==  ESR = 0xbe000000  FAR = 0x600084000
```

`0x600084000` is APCIe port 0's second window, which SART bootloader entry 0
permits, so that is ANS reaching the storage link. `ps_pcie_ref` alone was not
enough; `ps_apcie`, `ps_apcie_gp` and `ps_apcie_st` are all pinned now. No
driver owns the complex and iBoot already trained the link, so Linux leaves it.

### 3. T8020 has the NVMMU but not the linear submission queue

`apple_nvme_hw` had one `has_lsq_nvmmu` flag for two features. iBoot leaves
`LINEAR_SQ_CTRL=0x0` and `NVMMU_NUM_TCBS=0x3f`, so this part has the NVMMU and
submits through a ring. Proved by contradiction: the flag off brings the fetch
error back. It is now `has_nvmmu` and `has_linear_sq`, and T8020 is the first
part to set one without the other.

### 4. The AIC never pointed the completion interrupt at this core

```text
queue at timeout: sq_tail=1 cq_head=0 cq_phase=1 cqe[0]=... 0001
```

The firmware posted a valid completion and the driver never saw it. Self
inflicted: `aic_irq_set_affinity` had been cut to not write `AIC_TARGET_CPU`,
which worked for the mailbox and UART only because iBoot had aimed those. See
[AIC](#no-aic-interrupt-is-ever-delivered) for the numbering; the value is
`BIT(AIC_WHOAMI)`.

### 5. The SMART log looked like it killed the firmware

```text
assert failed: [11956]:NVME_PERM_ERR F2H 1 SL[0] ERR 0x408 ... LBA 0x64013200
```

Blamed on worn flash behind a SMART log read, and `CONFIG_NVME_HWMON` was
disabled. It was fault 7: a SMART log read is an admin command with a buffer,
and half of those landed in a ring slot with an empty translation block. With 7
fixed, hwmon is back on and the log reads fine. Worth keeping because
`nvme_init_ctrl_finish` turns a hwmon failure into a failed controller reset, so
the next unrelated admin fault looks like this again.

### 6. Set Features has to come before Create IO CQ

`apple_nvme_reset_work` called `nvme_set_queue_count` after creating both
queues. M1 does not care; T8020 answers Create IO CQ with status 2 until
something has asked for a queue. Moving those lines up creates the CQ.

### 7. The NVMMU indexes translation blocks by ring slot

Two symptoms, one bug. Create IO SQ refused:

```text
host_ans2.c:1545: cmd parsing error for tag 0 fast decode err 0x4
```

and every post-Identify admin command with a buffer dying with
`NVME_PERM_ERR ... mmu[fffffff7, ...]`. The driver filled `tcbs[tag]`, right on
a linear queue where tag is slot, wrong on a ring. The admin queue has two
entries and one tag, so every command is tag 0 while the slot alternates, and
the firmware reads by slot, so every odd command found slot 1 empty. Identify is
slot 0, Set Features slot 1 (no buffer), Create IO CQ slot 0, Create IO SQ slot
1: exactly the pattern seen. Fill by slot. Invalidation still takes the tag; by
slot it asserts `duplicate tag error for tag 24576` on the third command.

`NVME_PERM_ERR` had also been read as a SART denial, and the driver permitted
all of DRAM for a while on that basis. It was never the SART: one entry per
queue is enough, and data buffers need none because they go through the NVMMU.

Ruled out first, all down to the slot: IO queue depth 64 and 16, `CC.IOSQES` 6
and 7, 64 and 128 byte entries, `NUM_TCBS` 15 and 63, the 0x1200/0x1208 base
registers in either order, `MAX_PEND_CMDS` on and off. Two experiments pointed
at it: skipping admin translation blocks broke Identify too, and skipping Create
IO SQ got the firmware reading `LBA 0x106b106b` (0x106b is Apple's PCI vendor
id), what it reports from an empty block.

### What iOS programs that this driver does not

| What | Where |
|---|---|
| IOSQ base | `nvme + 0x1200`, after Create IO SQ |
| IOCQ base | `nvme + 0x1208`, after Create IO CQ |
| "modesel" | `nvme + 0x1304`, `SetModeselRegister(uint32_t)` |

The first two are written but nothing has shown they are needed. `0x1304` reads
0 before and after ANS boots, and storage works without it. iOS also pushes ADT
blobs as vendor tunnel commands, opcode 0xb1 (`namespaces`,
`power-budget-platform-modes`, `low-latency-profile`, `nand-debug`); none are
needed for reads.

### What the ADT settles

| Thing | Address | From |
|---|---|---|
| ASC wrapper | 0x277400000 | ans reg index 0 |
| mailbox | 0x277408000 | wrapper + 0x8000 |
| coprocessor control | 0x277400044 | wrapper + 0x44 |
| NVMe registers | 0x27acc0000 | ans reg index 3 |
| SART | 0x27ac50000 | sart-ans reg |

`nvme-interrupt-idx = 4` means the fifth ans interrupt, 371, is NVMe; the first
four are the mailbox.

Three things the ADT gets wrong read literally:

1. **The 4-byte range at 0x27ad20044 is a decoy.** It looks like a coprocessor
   control register (base + 0x44) and accepts a write to the run bit, but starts
   nothing. Bit 4 of 0x277400044 does. Point the nvme "ans" reg at 0x27ad20000
   and it probes clean then fails "ANS did not boot".
2. **The mailbox is the T8015 kind** even though the control register is where
   T8103 puts it. From a parked m1n1: `mbox+0x108 = 0x00020001` and
   `mbox+0x10c = 0x00100101` are live (T8015 layout), `+0x110`/`+0x114` dead
   (v4). Claim `apple,asc-mailbox-v4` and the handshake times out.
3. **The interrupt order is not the binding's order.** The ADT lists 365, 364,
   367, 366, two descending pairs. Read each pair as (not-empty, empty) and it
   comes out ascending like every other Apple SoC, and 367 fires.

### sart-version 1

The ADT says `sart-version = 1`; neither Linux nor m1n1 has a case for it (they
know 0, 2, 3, and m1n1 4). v0 and v2 share register offsets and differ in field
widths. iBoot's leftover entries say v2: one reads config `0x2f000004`, bit 29
set, which fits v2's 8-bit field at 31:24 but not v0's 5-bit field at 28:24, and
iBoot writes `0x6f`/`0x6a` elsewhere, needing seven bits. The paddr shift is 12:
entries 1, 2, 3, 4, 8 all land in DRAM shifted by 12 and nowhere near it shifted
by 14. v2 also gets furthest in practice: the coprocessor DMAs its syslog back.

### The PCIe reference clock, the first wall

Same SError as fault 2 (`FAR = 0x600084000`), same cause as the AIC: nothing
claims `ps_pcie_ref`. It has no parent, and the nvme node names `ps_ans2` and
`ps_apcie_st`, so `ps_pcie_ref` is left unused and switched off. Pinning it made
the fault rare; `ps_apcie`, `ps_apcie_gp` and `ps_apcie_st` had to be pinned
too. Twice now an unclaimed domain was the root cause: when a block answers at
probe then misbehaves, check `ps_*` first.

### What the iOS kernelcache says

Do this early next time:

```sh
ipsw kernel kexts work/*/kernelcache.release.* | grep -iE 'sart|nvme'
ipsw kernel extract work/*/kernelcache.release.* com.apple.iokit.IONVMeFamily -o .
strings -n 8 com.apple.iokit.IONVMeFamily
```

`IONVMeFamily` settles the variant: LinearSQ belongs to ANS3
(`AppleANS3NVMeController::EnableLinearSQ`), and `AppleANS2NVMeController`, the
class for this SoC, has no LinearSQ strings. The ADT agrees (`role = ANS2`).

But half of that reasoning was wrong: the absence of "NVMMU" strings did not
mean the block is absent, only that Apple does not call it that. The hardware
has it, iBoot leaves `NVMMU_NUM_TCBS` at 0x3f, and disabling it brings the fetch
error back. A string search proves a name absent, not a feature. Read the
registers the bootloader left before concluding from `strings`.

`AppleSART` is less useful: this SoC names `sart,coastguard`, which maps to
`IOCoastGuardSARTMapper`, which writes no registers (it calls
`pmap_iommu_ioctl(..., SART_IOCTL_SET_ACTIVE, ...)` into XNU's PPL). The v1
register semantics are in the PPL, not the kext.

### Two traps

- **Stale crashlogs.** ANS keeps its crashlog across a reset and RTKit reports
  whatever it finds at init. One boot reported a PC and FAR from two boots
  earlier. Compare crash times; do not trust one boot's dump.
- **No /dev/mem.** arm64 rejects MMIO above RAM even with `CONFIG_STRICT_DEVMEM`
  off (`Bad address`). Use a parked m1n1 and `p.read32()`/`p.write32()` from a
  script that imports `m1n1.setup`. `p.nvme_init()` is not a shortcut: it stops
  at `asc: Unsupported compatible`, not knowing `iop,ascwrap-v2`.

## The SMC, which is battery and buttons

`/arm-io/smc` is an `iop,ascwrap-v2` with RTKit behind it, the same shape as
ANS, and it came up first try. Linux already has every driver for it, and they
were all running and finding nothing because no node existed.

Addresses, and A12 matches T8103 exactly:

| | |
|---|---|
| ASC wrapper | 0x23e400000, 0x20000 |
| mailbox | 0x23e408000, ASC + 0x8000 |
| SRAM | 0x23fe00000, 0x50000 |
| interrupts | 253 to 256 |

The SRAM is the part worth writing down: it is not in the SMC node's `reg` at
all. It is `region-base` and `region-size` on the child
`/arm-io/smc/iop-smc-nub`, which also names the firmware, `t8020smc`. The
node's `reg` second entry, 0x23e050000, is something else and is not what the
driver wants.

The ADT lists the interrupts as 254, 253, 256, 255, two descending pairs,
exactly as it does for ANS. Read each pair as (not-empty, empty) and they come
out ascending in the order the binding wants.

No `power-domains`. `clock-gates` and `power-gates` on the ADT node are both
empty, which is what you would expect of the thing that runs when the rest of
the SoC does not.

The compatible is `apple,t8015-smc` rather than the T8103 one, so the MFD
instantiates the A11 cell list: input, power, gpio, hwmon and reboot, with no
RTC. `macsmc-power` and `macsmc-input` need no node of their own.

What works, read over telnet:

```text
/sys/class/power_supply/macsmc-ac       Mains
/sys/class/power_supply/macsmc-battery  Battery
capacity 51   capacity_level Normal   health Good   cycle_count 601
charge_full 2683000   charge_full_design 3156000
voltage_now 3906000   current_now 444000   power_now 1734000   temp 294
charge_behaviour [auto] inhibit-charge force-discharge
```

So battery, charger detection, battery temperature and the power button, which
arrives as `Apple SMC power/lid events` on input0.

`macsmc-hwmon` does not probe, which is expected: it says "No valid sensors
found of any supported type" because it looks for Mac sensor key sets. The
SoC's own sensors are separate, see [die temperature
sensors](#die-temperature-sensors).

### Poweroff, and the PMU scratchpad

`macsmc-reboot` is the SMC's poweroff cell. It wanted four nvmem cells that no
node provided, so it used to return `-ENODEV`. The cells live in the PMU, not
in the SoC, which is why wiring it up means adding a whole SPMI bus.

| | |
|---|---|
| SPMI | 0x23d180700, 0x100 |
| PMIC | slave id 0xf, `pmu,imola` |
| scratchpad base | 0xa000 |

The ADT node `/arm-io/spmi` lists three register ranges and 27 interrupts. The
driver takes the first range and no interrupts. The PMIC's scratchpad base is
`info-leg_scrpad` on `/arm-io/spmi/spmi-pmu`, 0xa000 here, with the regular
`info-scrpad` right after it at 0xa028. Everything the reboot handler touches
is in those first 0x28 bytes, at the offsets T8015 and T8103 also use:
`boot_stage` at 1, `boot_error_count` at 2 bits 0-3, `panic_count` at 2 bits
4-7, `shutdown_flag` at 0xf. The flag is a whole byte, not a bit, because the
driver writes 0x10 or 0x90 into it.

Proof the base is right, from the first boot with the node:

```text
macsmc-reboot macsmc-reboot: PMU logged 10 boot error(s) and 0 panic(s)
macsmc-reboot macsmc-reboot: Handling reboot and poweroff requests via SMC
```

Ten boot errors is real history from all the failed boots, read back out of the
scratchpad. A wrong base reads zeroes.

The compatible is `apple,t8015-smc-reboot`, the one without the `phra` restart
key, so the driver registers poweroff only and a restart falls through to the
watchdog at 0x23d2b0000. Both work:

| command | result |
|---|---|
| `poweroff -f` | off, USB gone, no `05ac:` device left |
| `reboot -f` | back as `05ac:1281`, recovery mode |

Plain `poweroff` and `reboot` in the test ramdisk do nothing; busybox hands
them to init and init drops them. The `-f` goes straight to the syscall.

Staying off rather than bouncing straight back into recovery is what
`shutdown_flag` buys. Reboot ends in recovery because there is no OS on the
flash, which is normal here and not a failure.

One harmless warning per boot, three times:

```text
OF: Bad cell count for /soc/spmi@23d180700/pmic@f
```

The PMIC takes a two cell address from the bus and declares one cell addresses
for its own children. Upstream Apple device trees are shaped the same way.

## Display, what is known so far

No driver yet, but the pipe is under control: the scanout address can be
changed and the picture moves, which is the hard part. See [the write
aperture](#writes-go-to-the-alias-at-0x230200000-not-to-0x230000000).

**Every Linux piece except the pipe already exists.** The names in the ADT are
the same ones the Touch Bar on M1 uses, which is the hardware the `adp` driver
was written for:

| ADT | address | Linux driver |
|---|---|---|
| `/arm-io/disp0`, `disp0,t8020` | 0x230000000, 0x2f0000 | nothing fits, see below |
| `/arm-io/dart-disp0`, `dart,t8020` | 0x230704000 | `apple-dart` |
| `/arm-io/mipi-dsim`, `mipi-dsim-1,synopsys` | 0x230400000 | `adp-mipi`, its own DSI host |
| `/arm-io/mipi-dsim/lcd`, `lcd,summit` | | `panel-summit`, `apple,summit` |
| `/arm-io/i2c3/display-pmu`, `display-pmu,acorn` | 0x23501c000, IRQ 411 | nothing |

So the panel driver is already upstream and so is the DSI host. The missing
piece is the pipe itself.

**adp's register map does not describe this pipe.** `adp` wants a `be` and an
`fe` window. T8103 has them 0x200000 apart, and T8020's single 0x2f0000 range
is big enough for the same spacing, so that was the theory. It is wrong:

```text
0x230000000 +0x000  0x21508007    0x230200000 +0x000  0x21508007
0x230000000 +0x00c  0x0293648c    0x230200000 +0x00c  0x0293658c
0x230000000 +0x034  0x4008e032    0x230200000 +0x034  0x4008e712
```

Those two windows read the same at +0, and the other two offsets drift between
reads, by 0x100 and 0x6e0 in one pass. They are counters in a pipe that is
actively scanning out, not `ADP_SCREEN_SIZE` and `ADP_INT_STATUS`. The reads at
adp's back end offsets return high entropy values with no framebuffer address
and no stride in them.

**The iOS side says why.** The kext is `AppleMobileDispH11P`, 1.8MB of the full
IOMFB stack: `IOMFB::UPPipe_H11P`, `UPBlock_GenPipe_v2`, `UPBlock_Blend_v1`,
`UPBlock_PCC_v1`. On M1 that same stack runs on the DCP coprocessor; on A12 it
runs on the main CPU. `adp` is a much smaller, older pipe. Getting the plane
registers means reversing this kext:

```sh
ipsw kernel kexts work/*/kernelcache.release.* | grep -iE 'clcd|disp|mipi'
ipsw kernel extract work/*/kernelcache.release.* \
    com.apple.driver.AppleMobileDispH11P -o .
```

`AppleSynopsysMIPIDSI` and `AppleAcornDisplayPMU` are the other two, 99KB and
66KB. Acorn is the OLED rail controller, 8 bit registers over I2C
(`AppleAcornDisplayPMU::writeReg(uint8_t *, uint8_t *)`), and has no brightness
strings in it at all.

**Brightness needs the pipe, there is no shortcut.** `panel-summit` sets it
with `mipi_dsi_dcs_set_display_brightness`, a DSI command to the panel, which
matches `DBVMax = 2047` and `override-boot-brightness = 740` on the ADT's
`/backlight` node. The DWI block exists on this SoC, `/arm-io/dwi` at
0x23b200000, and `apple,dwi-bl` binds to it, but its binding says plainly it is
for LCD phones. Measured: the driver probes, the `dwi` power domain is on, the
device appears as `/sys/class/backlight/23b200010.backlight` with
`max_brightness` 2047, and writes do not stick. `actual_brightness` stays 0 and
the screen does not change. The node is not in the tree, because it does
nothing.

### The pipe register map, from the kext

Read out of `AppleMobileDispH11P` with Ghidra. It has no symbols, so the method
was: find a C++ signature in the strings, take the data xref to the function
that logs it, and read the register helpers out of the decompilation.

Three helpers do all register access, and finding them is the whole trick:

| function | what it is |
|---|---|
| `FUN_fffffff00904c4d4(stream, off)` | read one word, `*(u32 *)(base + off)` |
| `FUN_fffffff00904c50c(stream, off, val)` | write one word |
| `FUN_fffffff00904c540(stream, off, buf, n, ..)` | write n words from a buffer |

With those named, a literal search of the decompiled code for `0x8000 + 0x5`
finds every GenPipe register in the kext, because each one is written as
`instance * 0x8000 + offset`.

**Blocks.** The plane fetch unit, which Apple calls GenPipe, starts at 0x50000
with 0x8000 per instance. A second copy of several registers sits 0x1000 up
(0x51004, 0x51008), used when a flag in the driver's own state is set.

| offset | what the kext does with it |
|---|---|
| 0x50000 | written `-(enable & 1)`, so all ones or zero |
| 0x50004 | bit 31 reads back as enabled, written 0 to disable |
| 0x5000c, 0x50010, 0x50020 | written 0 or a small constant during setup |
| 0x5001c | the big format and config word, built from the surface |
| 0x50028 + plane*4 | per plane format bits |
| 0x50030 + plane*4 | **surface address**, masked to 64 bytes |
| 0x50040 + plane*4 | second address, masked to 64 bytes |
| 0x50048, 0x50058 + plane*4 | two more addresses, masked to 128 bytes |
| 0x50060 + plane*4 | per plane stride |
| 0x50068, 0x50070 + plane*4 | per plane width and height pairs |
| 0x50078 | source size, `w \| h << 16` |
| 0x5007c, 0x50080 | destination size pairs, read back as `w = val >> 16` |
| 0x50084 to 0x50090 | crop, four pairs of 10 bit fields |
| 0x50094 | **commit**, written `(mask & 0xf) \| 0x100` |
| 0x50098, 0x500a8 + n*4 | per plane compression words |
| 0x500b8 to 0x500d8 + plane*4 | scaler ratios |
| 0x500e0 | dirty flags, which sub-programs changed |
| 0x500e4, 0x500f0, 0x50114, 0x50120, 0x50150 | colour matrices |
| 0x5015c, 0x50160, 0x50184 | small flags and an acknowledge |
| 0x50170 | bandwidth, one byte |
| 0x52000 + n*0x808 | three gamma tables |
| 0x53818, 0x53c98 | scaler coefficient tables |
| 0x54118 + n*0xda0 | three more tables |

Outside GenPipe, from `swap_flush_stream` and the layer setup it calls:

| offset | what |
|---|---|
| 0x4602c | swap commit, `(frame & 0xf) << 8 \| 0x1000` |
| 0x8cd8 | frame id, `frame & 0xf` |
| 0x8cdc + layer*4 | per layer enable and format, four layers |
| 0x8cec + layer*4 | per layer size pair |

**What this means for a driver.** The surface address is 32 bits masked to 64
bytes, so it is an IOVA through `dart-disp0` and not a physical address. A
minimal driver does not have to program any of the format, scaler or gamma
registers: iBoot already did, and the picture is on screen. It has to map a
buffer through the DART, write the IOVA to 0x50030, the stride to 0x50060, and
commit with 0x50094 and 0x4602c.

**Verified on the phone.** The window base is 0x230000000 and the map is right:

```text
+0x050004  0x80000001   bit 31, the pipe is enabled
+0x050080  0x04da0a80   1242 x 2688
+0x050030  0xf7cd4000   the framebuffer, boot args say 0x8f7cd4000
+0x050060  0x00001380   stride 4992
```

The surface register holds the low 32 bits of the physical framebuffer, so
`dart-disp0` flat maps it the same way our USB DART does.

### Writes go to the alias at 0x230200000, not to 0x230000000

**This is the thing to know.** The disp0 window is mirrored every 0x200000.
Reads work through either copy. Writes only land through the second one:

```text
write 0x230250030 <- 0xf7cd5000
read  0x230050030 -> 0xf7cd5000     the write landed
write 0x230050030 <- anything       dropped, silently, no fault
```

So the plane is programmed at 0x230200000 + offset and read back at
0x230000000 + offset. Every register that looked read-only takes writes
through the alias.

Proven by moving the picture. Writing the surface address and then the plane
commit at 0x50094 shifts what is on screen immediately:

| write | what the screen did |
|---|---|
| surface + 4 bytes | image moves left one pixel |
| surface + 400 bytes | image moves left 100 pixels |
| surface + stride * n | image moves up n lines |

Increasing the address moves the image left and up, which is the normal way a
scanout origin behaves, so there is no rotation to undo. One early reading
looked like a shift to the right: that run still had a stale +0x1000 from an
earlier probe, which is 1024 pixels of a 1242 pixel line, so it wrapped and
looked like a small shift the other way. Reset the surface between
experiments.

Writing 0xf7cd4000 back to 0x230250030 puts the picture back exactly.

**What a driver needs, then.** Allocate a buffer, map it through
`dart-disp0`, write the IOVA to 0x230200000 + 0x50030, commit with 0x50094,
and that is a page flip. Nothing else has to be programmed, because iBoot
already set the format, the size, the stride and the panel.

### What the write split in the kext actually was

Before the alias was found, the measurements looked like two write paths in
the hardware, because they line up with two helpers in the kext:
`FUN_fffffff00904c6ec` writes directly, `FUN_fffffff00904c540` goes through
`AppleRegisterStream`. The registers that took writes at 0x230000000, 0x8cd8
and the two layer registers, are exactly the ones the kext writes directly.

That was a coincidence of which registers live where, not two mechanisms.
`FUN_fffffff00904c738`, the batch writer under the stream, is also plain MMIO
stores. The stream is about batching and chunking large uploads, not about
owning registers.

Two hypotheses died on the way, both worth not repeating:

- **Power domains.** All of `disp0_busif`, `disp0_fe`, `disp0_be`, `mipi_dsi`,
  `disp0_gp0`, `disp0_gp1`, `disp0_ppp` and `disp0_hilo` already read target 15
  actual 15 from iBoot. `disp0_be_2x` and `disp0_dsc` were off; turning them on
  changed nothing about the dropped writes. Writing those two also appears to
  be what killed the proxy that session, so leave them alone.
- **A second register bank.** The kext mirrors the plane 0x1000 up, so 0x51000
  looked like a writable shadow. It reads mostly zeros and drops writes too.

### The driver owns the display, the panel is black

`patches/linux-0007` adds `drivers/gpu/drm/tiny/apple-h11p.c`, a DRM driver on
`drm_simple_display_pipe` plus the GEM DMA helpers. It reads the mode from
0x50080 and the stride from 0x50060, takes the screen off simpledrm, and
programs surface and stride through the write aperture.

Where it stands: the driver probes, simpledrm goes away, `fb0` is
`apple-h11pdrmfb`, fbcon binds to it, the shell stays up and the phone does not
crash. The panel is black. Writing to `/dev/tty0` changes nothing on screen.

Two real bugs were found and fixed on the way, both worth knowing:

- **No `.fops` in the `drm_driver`.** `DRM_GEM_DMA_DRIVER_OPS_*` does not
  provide them, and `drm_fbdev_dma_fb_open()` goes straight through
  `driver->fops->owner`. Opening the framebuffer oopsed, which is what fbcon
  does when it binds, so every boot that took the console died exactly there.
  The trace is unmistakable once it can be read:
  `drm_fbdev_dma_fb_open+0x14` under `chrdev_open`.
- **Reprogramming the plane on every damage.** fbdev renders into a shadow and
  the damage path calls back into the driver at the console's update rate,
  always with the same address. Programming a live scanout that often corrupts
  the picture and eventually takes the phone down. The driver now compares
  against what it last wrote and touches nothing when neither address nor
  stride moved.

Three things that looked like the cause and were not, each disproved rather
than argued about:

- **Frame synchronisation.** Sixty flips from the m1n1 proxy, alternating two
  addresses 16ms apart, raise no exceptions and leave the phone alive. A
  guessed version of the kext's swap sequence only crashed earlier.
- **Register write spacing.** `settle_us=0`, back to back writes, with the
  driver cut down to a single allocation and a single flip: survives.
- **The end address at 0x50040.** iBoot leaves it zero, and writing one looked
  like the cause of a picture repeating down the screen. The eight band test
  from the proxy wrote the same computed value and came out perfect. The
  driver no longer writes it, because iBoot does not either.
- **A pitch mismatch.** The repeating, sheared console looked like fbcon
  drawing at one stride while the hardware scanned at another.
  `/sys/class/graphics/fb0/stride` reads 4992, exactly what the hardware has.

**What is left.** The pipe is told to fetch our buffer and the readback agrees,
`flip to 0x06400000 stride 4992, reads back 0x06400000`, and fbcon is bound and
drawing, and the panel shows nothing. So either the damage blit never reaches
the buffer the pipe is fetching, or something puts the plane back afterwards.
A watcher that logged the live register once a second was the obvious next
step and crashed the phone on its own, which says the margins here are thin.

Boots are also not repeatable: the same image has produced a repeating
console, a black console, and a hang, which is its own problem and probably
needs solving first. **ramoops** would be the way, so a crashing boot can be
read back instead of guessed at.

### Reading disp0 without losing the proxy

A bus fault here wedges m1n1, which costs a DFU trip, so this is worth getting
right:

- **Power the domains first.** `p.pmgr_adt_power_enable("/arm-io/disp0")` and
  the same for `dart-disp0` and `mipi-dsim`. Without that, 0x230004030 raises
  an SError. With it, the same read returns a value.
- **`GUARD.SKIP` does not save you.** `p.set_exc_guard()` is set and the proxy
  still stopped answering on the first fault. Treat one fault as the end of the
  session.
- **Do not scan.** 0x230100000 faults even with the domains up. Read a short
  list of addresses chosen in advance, cheapest first, and `flush=True` every
  line so the last line printed names what killed it.

Boot args, for reference: framebuffer at 0x8f7cd4000, 1242x2688, stride 4992,
which is 1248 pixels at 4 bytes and not 1242.

## Die temperature sensors

Nine of them in the ADT, all `tempsensor,t8020`, in three blocks. Linux has no
driver, so `patches/linux-0006` adds `drivers/hwmon/apple-soc-temp.c`, which is
hwmon only: no thermal zones, because there is nothing to throttle with cpufreq
off and no fan to turn.

| ADT node | block | base | registers |
|---|---|---|---|
| tempsensor0 to 4 | PMGR die | 0x23b288000 | 32 bit, 0x4000 per sensor |
| tempsensor5 to 7 | P cluster | 0x211e30000 | 64 bit, at 0x0, 0x40, 0x200 |
| tempsensor8 | E cluster | 0x210e30000 | 64 bit, at 0x0 |

Every offset comes from the ADT node itself, which names them:
`sensor-offset-readSum` at 0x28, `sensor-offset-readCnt` at 0x30,
`sensor-offset-readBK` at 0x20000 for the PMGR block and 0x4000 for the
clusters, plus `CTL0-set`, `CTL0-clr`, `CTL1`, `CTL2`, `status` and four alarm
registers. `reg-64-bit` is what says the cluster sensors need `readq`.

Two things the ADT does not say, both measured:

**The accumulators are empty.** `readSum` and `readCnt` are zero on every
sensor, so iBoot does not leave the averaging running. `readCnt` is checked
anyway and the single `readBK` read is the fallback, which is what actually
gets used.

**A read is two 16 bit fields.** `readBK` on sensor 0 was `0x8a4f0792`. Across
the nine sensors the high half ran 0x8a4d to 0x8a5d and the low half 0x073a to
0x079e, moving in opposite directions, so the high half is the raw diode code
and the low half is the temperature. The low half divided by 64 gives 28.9 to
30.5 degrees, against 29.4 from the SMC's battery sensor at the same moment.
Divided by 16 it would be 121 degrees.

Then six busy loops for 45 seconds, which moved it the right way and by a
sensible amount:

| sensor | idle | loaded |
|---|---|---|
| SOC die 0 | 31.5 | 33.7 |
| ACCp0 | 30.8 | 34.6 |
| ACCe | 29.3 | 33.1 |

PMGR sensor 2 reads zero in both its status and its value while the other four
read normally, so the driver skips whatever reads zero instead of publishing a
channel stuck at 0 degrees. It says so once:

```text
apple-soc-temp 23b288000.tempsensor: SOC die 2: reads zero, skipped
```

## cpufreq, the part that completes transitions is not running

`CONFIG_ARM_APPLE_SOC_CPUFREQ` is off. With it on, the boot stops inside
`apple_soc_cpufreq_module_init`, and chasing that through Linux cost a lot of
DFU trips for very little. Driving the DVFS registers directly from the m1n1
proxy answered it in two sessions.

Cluster controllers are at 0x210e20000 (E) and 0x211e20000 (P). As iBoot leaves
them, both read:

```text
CMD 0x20 = 01900102   PS1=2, PS2=0, SET and BUSY clear
STATUS 0x50 = 00000022   CUR_PS=2, TGT_PS=2
PLL_STATUS 0xc0 = a0000000
PLL_FACTOR 0xc8 = 04200005 on E, 03f00005 on P
```

So `DVFS_STATUS` is the T8103 layout, CUR_PS at bits 7:4, which also matches
what the driver reports for the current frequency. What is not upstream's
assumption:

- **`DVFS_CMD` ignores 32 bit writes.** A `writel` changes nothing at all. A
  `writeq` of the same value moves `CUR_PS`. Reads work at either width, so
  upstream's `readq`/`writeq` is right and any 32 bit shortcut is silently
  useless.
- **`ioremap_np` wedges the E cluster.** With the DVFS block mapped
  non-posted, the P policy comes up and reads its status fine, then the first
  access to 0x210e20000 never returns. Plain `ioremap` gets further. That is
  the opposite of the rule everywhere else on this SoC, where non-posted is
  mandatory, so it is worth remembering that the rule is per block.

The transitions themselves are what kill it, measured by walking the pstates
one at a time from m1n1:

| cluster | result |
|---|---|
| E, pstates 1 to 4 | complete, `CUR_PS` follows each request |
| E, pstate 5 (1572 MHz) | hangs the SoC hard, m1n1 included |
| P, first transition | completes |
| P, every later one | `BUSY` sticks forever at CUR_PS=1, TGT_PS=2 |

A stuck `BUSY` on the P cluster is permanent: five seconds later it is
unchanged, while the E cluster sits happily at pstate 2 beside it. That is the
cluster the kernel runs on, so schedutil asking for the top of the table early
in boot is exactly the reset that was being chased.

None of that is a driver bug, and it is not the hardware refusing outright
either. The ADT says what is missing. `/arm-io/pmgr` has `cpu-apsc = 1`,
`clusters = 4, 2`, and two children that matter: `clpc`, Apple's closed loop
performance controller, carrying a full set of PID gains for utilisation,
scheduler latency and power zones, and `pmp`, the coprocessor it runs on. On
this generation DVFS is arbitrated by that controller rather than driven
register by register by the OS, and we never boot it. That is exactly the P
cluster symptom: the request is accepted, `BUSY` latches, and nothing ever
completes it, because the thing that completes it is not running.

The frequencies, which used to live in the device tree as OPP tables and are
kept here now that nothing can use them. Read from a live system with the
PongoOS `dt` command, from `voltage-states1-sram` (E) and `voltage-states5-sram`
(P); the copies in the IPSW are zeroed. `opp-level` is the table index plus one,
as on A10 and A11, and iBoot leaves both clusters at level 2.

| pstate | E, Tempest | P, Vortex |
|---|---|---|
| 1 | 528 MHz | 504 MHz |
| 2 | 792 MHz | 744 MHz |
| 3 | 1056 MHz | 1176 MHz |
| 4 | 1308 MHz | 1704 MHz |
| 5 | 1572 MHz | 2136 MHz |
| 6 | | 2376 MHz |
| 7 | | 2436 MHz, boost |
| 8 | | 2496 MHz, boost |

Latencies, in the same order, were A11's: 1800, 140000, 105000, 115000 and
125000 ns on E, and 1400, 140000, 110000, 110000, 125000, 130000 ns on P.

The pstate frequency and voltage table is not in the ADT at all, so iBoot
programs it into the cluster block from somewhere else. Two ways forward if
this ever matters: bring up the PMP and CLPC path, which is an ANS2 sized
coprocessor project, or find the per-pstate configuration registers in the
cluster block and drive the state machine directly. The cheap first look for
the second is to dump the cluster registers around the DVFS block on both
clusters and diff them, since the E cluster manages four pstates and the P
cluster manages one.

None of this blocks anything. The phone runs pinned at pstate 2, 744 MHz on the
P cores and 1056 MHz on the E cores.

## Reading the console at all

simpledrm's fbcon paints in lagging bursts, so a quiet boot looks like it died
at the last thing that got flushed, and the apparent hang point moves with how
much is being logged. `boot_delay=8` paces printk enough for the console to keep
up, and only then does the screen show where it actually stopped. With
`initcall_debug` on top, the hang is the last `calling` with no matching
`returned`, which is how the cpufreq hang was found. `boot_delay=150` slows it
enough to film, and `panic=0` keeps a panic on screen.

`CONFIG_FB_SIMPLE` instead of simpledrm is not an escape: it builds and lands in
`System.map` but never binds, giving no output at all. For hang hunting,
`KCONFIG_EXTRA="--disable CONFIG_DRM_SIMPLEDRM --enable CONFIG_FB_SIMPLE"` plus
the lockup detectors is what to reach for, knowing it may print nothing.

`g_multi` is a red herring. It fails early with `couldn't find an available UDC`
because dwc2 is still deferring on its phy, and later `failed to start g_multi:
-22`. Neither matters: the initramfs builds its own gadget through configfs and
that one binds.

Also wasted an evening: the `$(IMAGE)` rule had no prerequisites, so once
`Image.gz` existed, edits under `build/linux` never reached the blob. It depends
on `FORCE` now. Check the timestamp of the object you changed before trusting a
test.

## Why no hypervisor target

m1n1's hypervisor would trap the guest's UART writes and give Linux an early
console for free, but it needs EL2. Nothing in this chain has been shown to hand
over at EL2, and the ADT's `has-virtualization = 1` is about the silicon, not
the exception level.

## Corrections

Things this repo previously asserted that are wrong.

- **"Any repacked initramfs panics the kernel."** No. Generalised from two
  failures of a flaky chain. `init/initramfs.c` handles concatenated archives
  and the repacked one boots. The real bug was in the injected script: at
  `rdinit=` time busybox has not run `--install -s`, so `/bin/sh` does not
  exist.
- **"Not the USB DART."** It was the USB DART. The reading that cleared it was
  taken on the old boot chain, where something else had already programmed the
  DART, so bypass was never actually what the gadget ran with.
- **`05ac:12a8` is our gadget.** Different phone. Ours is `05ac:4142`.

## Known gaps

1. **cpufreq.** Off. Needs the CLPC coprocessor, see
   [cpufreq](#cpufreq-the-part-that-completes-transitions-is-not-running).
2. **Chicken bits.** Applied in m1n1 at startup; the kernel does not reapply
   them per-core. Fine for bring-up.
3. **The first USB attach still fails, the gadget just retries until it does
   not.** See [the self replug](#the-self-replug). The link always comes up
   now, it can take 35s. Why the first attach fails is not known.
4. **The display is black.** The driver owns the screen and the phone stays
   up, but nothing fbcon draws reaches the panel. See
   [display](#the-driver-owns-the-display-the-panel-is-black).
5. **Display colours are wrong.** The pipe scans out 30 bit pixels and fbdev
   can only ask for 32, so the console comes out light blue. Needs the format
   register at 0x5001c.
